### 3.9 The attention's K/V blocks staged through LDS for eight waves: 1.10–1.14x on the kernel, bit-identical, a 480p forward 25.2 → 24.3 s — **done** ✅ (2026-09-30)

**Question** (KERNELS.md G4b, left by §3.8): the transposed attention
(`h3_attn_t_qt2_kt4`, one wave32 a workgroup, 32 queries) loads every K
and V fragment of every key block itself, 128 fragment loads beside 128
MMAs, and §3.8 priced those loads at 11–12 points. §2.9's lever on the
GEMM was the slab fetched once a workgroup, ahead, and shared through
LDS. §3.8 estimated it here at "the 12 memory points less 6–9 of LDS reads
and barrier, ≤ 2% of a forward" and did not build it. Is that the number?

**Answer: it is 10–14% on the kernel and 3.7% on a forward, bit-identical,
and it ships for `h3/dit`.** The estimate missed two things: the build is
spill-free at one query tile a wave, so §3.8's exact softmax knobs
(`LAZY`, `TAIL_SPLIT`) — dead at 256 VGPRs with 112 spilled — are worth
6–10% on it; and the fetch is a quarter of the bytes, which the clock
shows (2657 → 2717 MHz over a forward).

| 480p forward, int8 bank, two runs each, interleaved | attention (100 dispatches) | forward | sclk |
|---|---:|---:|---:|
| the one-wave build (`H3_ATTN_LDS=0`) | 9.79 / 9.82 s, 37.1–37.2 TFLOP/s | 25.23 / 25.21 s | 2653–2660 MHz |
| **`h3_attn_t_kvlds_w8_kt4`** | **8.91 / 8.90 s, 40.8–40.9 TFLOP/s (1.10x)** | **24.27 / 24.35 s (1.037x)** | 2717–2718 MHz |
| 768p, one run each | 60.5 → **54.3 s** (34.6 → 38.6 TFLOP/s, 1.115x) | 95.9 → **92.5 s** (1.037x) | 2658 → 2704 MHz |

Every new-build forward is bit-identical to the control's
(`H3_GEMM_REF`, both shapes); `TestGPUForward` and `TestGPURun` pass on
the new default.

#### The build

`-DKVLDS=1 -DWAVES=8 -DQT=1 -DKTIL=4 -DLAZY=1 -DTAIL_SPLIT=1` on
`h3_attn_t.comp`. A workgroup is eight wave32 waves, a query tile each
(128 queries), over one head. A key block (64 keys) is 16 KB of K and
16 KB of V^T; the workgroup's 256 lanes fetch each as four `uvec4` a lane
and write them to two LDS planes:

- K: 64 key rows of the head's 128 components at a pitch of 132 halves;
- V^T: 128 component rows of the block's 64 keys at a pitch of 68 halves;

both 2 dwords mod 32, so the sixteen lanes of a fragment's `ds_load_b64`
land on sixteen different bank pairs (§2.9 item 3). 34.8 KB of LDS, one
workgroup a CU, four waves a SIMD, 256 VGPRs, nothing spilled.

One plane each — two K planes and two V planes are 68.6 KB and the limit
is 64 — so a block has two barriers, not the GEMM's one:

```
top of block b:   fetch K(b+1) into 16 staging registers
S^T = K(b).Q^T    32 MMAs, fragments from the K plane
barrier           every wave is done with K(b)
store K(b+1); fetch V(b+1)
softmax
O^T += V(b)^T.P^T 32 MMAs, fragments from the V plane
barrier           every wave is done with V(b)
store V(b+1)
```

Each fetch is in flight for half a block (32 MMAs, 544 clocks, the
GEMM's slab depth) and is fetched and stored inside one trip of the loop.
The same MMAs in the same order per accumulator as the one-wave build at
the same `KTIL`, so the context is the same bits; a wave whose queries
start past the sequence runs the loop (the barriers need it) and stores
nothing.

#### What it says

1. **A register carried across a loop's back-edge is copied there, behind
   a wait for whatever it holds.** The first cut fetched a block ahead
   into staging registers that lived across the back-edge. The
   disassembly: the new fetch is issued into fresh registers, and the
   back-edge copies them into the phi's registers behind
   `s_waitcnt vmcnt(0)` — so every block waited out its own fetch, and
   the "block ahead" was no prefetch at all (8–9% by the L0 control).
   §2.9 found the same thing about fragments; it is true of plain `uvec4`
   too. The GEMM's staging has always been fetched and stored inside one
   trip, which is why it never showed. The same back-edge also rotated
   all 64 accumulator registers (37 `v_dual_mov`), which the restructure
   removed with it: the whole-block loop of the shipped build is 339
   non-MMA VALU beside 64 MMAs, 5.3 an MMA against the one-wave build's
   7.1, with ~160 moves.
2. **The exact knobs were dead only at the register limit.** §3.8 measured
   `LAZY`, `MAX_TREE` and `TAIL_SPLIT` inside ±2% on the one-wave build
   and concluded the allocator's moves redraw with every edit. On a build
   at 222 of 256 VGPRs with nothing spilled, `LAZY` (skip the rescale of
   O^T when no lane's max moved) is 3–4% and `TAIL_SPLIT` another 6%;
   `MAX_TREE` still loses. The allocator still decides: the three-knob
   build reads 131 + 136 moves in its disassembly and is 1.5% slower
   than the two-knob one.
3. **Two barriers a block cost 3%**, less than the GEMM's 6–9 for one a
   slab: the softmax between them is VALU work every wave does anyway.
4. **The fetch is a quarter of the bytes.** 32 KB a block for 128 queries
   where the one-wave build moved 32 KB for 32, and the forward's clock
   rises 60 MHz at the same package power.

**What is left in the kernel**, by the shipped build's controls: the
softmax 6%, the global side ≤ 6% (the L0 control also never moves a max,
so `LAZY` skips every rescale in it: an upper bound), the barriers 3%.
The three arms on the fetch's depth and the barrier's place all lost.

#### Carry-in

- **`h3/dit`: the default** wherever the transposed kernel runs
  (`AttnVariant{QT: 8, KTIL: 4, T: true}`; `QT` is query tiles a
  workgroup). `H3_ATTN_LDS=0` on `TestGPUShapes` is the control.
- **`h3/vae`: priced and left.** The head-64 build
  (`-DHEAD_DIM=64 -DSTORE_TAIL=0`, 17 KB of LDS, 192 VGPRs) reads 6.10 ms
  against the shipped `QT2 KTIL4`'s 6.22 on the VAE's screen (8 × 1,808
  keys), and two query tiles a wave 6.88: inside the screen's spread, on
  a kernel that is 14.5 VALU an MMA and a few percent of a decode. Not
  embedded.
- **`qimage/dit`: not carried.** Its transposed attention is opt-in behind
  the edit gate (§3.8) and this build is the same bits, so the gate's
  verdict is the same; the build would apply as it stands
  (`-DSTORE_TAIL=0`) if that gate is settled.

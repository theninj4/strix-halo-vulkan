### 5.1 Which memory type is fastest for GPU-read-only weights? — **DONE** ✅, **none of them, and the heap sizes are fiction**

**Two results, both negative, both worth more than the positive would have
been:**

1. **Memory type does not affect GPU read bandwidth on this part at all.**
   All eight types that can back a storage buffer read at **236.0–237.4
   GB/s** — a 0.57% spread across 32 cells of two runs, which is noise.
   Heap 0 averages 236.90 and heap 1 236.82, a ratio of **1.0004**.
   `DEVICE_LOCAL`, `HOST_CACHED`, `DEVICE_UNCACHED` and every combination of
   them are indistinguishable.
2. **The reported heap sizes are not limits.** RADV advertises heap 1 at
   83.79 GiB and heap 0 at 41.89 GiB. Memory type 3 — heap 1, the one
   `vk.NewBuffer` picks for everything — reserved **105.0 GiB**, and type 2 on
   heap 0 reserved **101.5 GiB**. Neither was refused by the driver; both
   stopped on the probe's own host-memory floor.

## What §5.1 predicted, and why it was wrong

The hypothesis was that `DEVICE_LOCAL|HOST_VISIBLE` "usually means
host-coherent/uncached-write-combine pages, which can read *slower* from the
GPU than plain `DEVICE_LOCAL`", and that since the whole decode path is
bandwidth-bound "a 10% difference here is a 10% tok/s difference". It expected
a ranked table and a free few percent.

There is no ranking. On this part every heap is the same LPDDR5X behind the
same memory controller, and the property bits describe **how the host sees the
pages** — write-combining, caching, coherency — not how the GPU's L2 and the
memory controller fetch them. A GPU read never goes through the CPU's cache
hierarchy, so `HOST_CACHED` buys it nothing and `DEVICE_UNCACHED` costs it
nothing. The intuition was imported from discrete parts, where `DEVICE_LOCAL`
means VRAM across a PCIe bus and the distinction is real.

## The measurement

`bench/ops_bank.go`'s memory-type arm, using the same `bank_gather.comp` probe
L0a verified: 1024 MiB read per timed step, drawn at random from a **12 GiB**
bank of each type, at the model's `gate_up` expert slab size. 12 GiB clears
two thresholds — the 32 MiB MALL, and the ~8 GB at which `cmd/bus` found the
character of a *host* read change. Each type is measured at a 1 GiB and a
12 GiB prefix, so a carveout effect would show as those two disagreeing.

| type | heap | 1 GiB | 12 GiB | flags |
|---|---|---|---|---|
| 0 | 1 | 237 | 237 | `DEVICE_LOCAL` |
| 2 | 0 | 237 | 236 | `HOST_VISIBLE\|HOST_COHERENT` |
| 3 | 1 | 236 | 237 | `DEVICE_LOCAL\|HOST_VISIBLE\|HOST_COHERENT` ← what everything uses |
| 5 | 0 | 237 | 236 | `HOST_VISIBLE\|HOST_COHERENT\|HOST_CACHED` |
| 7 | 1 | 237 | 237 | `DEVICE_LOCAL\|DEVICE_COHERENT\|DEVICE_UNCACHED` |
| 8 | 0 | 237 | 237 | `HOST_VISIBLE\|HOST_COHERENT\|DEVICE_COHERENT\|DEVICE_UNCACHED` |
| 9 | 1 | 236 | 237 | `DEVICE_LOCAL\|HOST_VISIBLE\|HOST_COHERENT\|DEVICE_COHERENT\|DEVICE_UNCACHED` |
| 10 | 0 | 237 | 237 | `HOST_VISIBLE\|HOST_COHERENT\|HOST_CACHED\|DEVICE_COHERENT\|DEVICE_UNCACHED` |

Types 1, 4 and 6 are excluded by the device: `vkGetBufferMemoryRequirements`
does not list them for a plain storage buffer.

New in `vk/`: `Device.MemoryTypes()`, `Device.NewBufferOfType()` and
`Buffer.Mapped()`, over two new shim entry points. Until now the engine could
only ask for the type it preferred and could not name one.

## Finding 3: this reconciles `cmd/bus`, it does not contradict it

`cmd/bus`'s doc comment records that "the first heap runs out at about **8 GB**"
because a *host read* of a mapped buffer gets 83x faster past that point
(0.18 → 14.10 GB/s). Allocation plainly does not run out at 8 GB — type 3 gave
105 GiB. Both observations are true and the reconciliation is the carveout:
`mem_info_vram_total` is **8 GiB**, so the first 8 GiB of type-3 allocations
land in real visible VRAM, which the CPU reads uncached and slowly, and past
that they land in GTT, which is ordinary cached system memory. The memory type
index never changes; the backing does.

**The part that matters here is that the GPU does not notice the boundary.**
Every type reads the same at a 1 GiB prefix and at a 12 GiB one, and L0a's
range sweep reads the same at 1 GiB and at 64 GiB. The carveau­t is a host-side
phenomenon end to end.

## Finding 4: freed GPU memory does not come back to `MemAvailable`

Found by having the capacity probe measure two types in one process and get
**zero** for the second. After the first probe releases 63 GiB,
`mem_info_gtt_used` drops to ~90 MB — the GPU really has let go — but
`MemAvailable` stays where it was, and `/proc/meminfo` accounts the pages under
none of `Cached`, `Slab` or `Shmem`. They are sitting in the driver's TTM page
pool, reusable by the GPU and invisible to the kernel's free-memory estimate.

Consequences, both practical:

- **The capacity probe measures one memory type per process**, and says so.
  Anything else reads a machine that looks full and is not.
- A serving process that allocates and frees weight banks will show a resident
  size that does not shrink. That is the pool, not a leak.

## The capacity numbers, and what they do and do not license

| memory type | heap | reported | reserved | stopped by |
|---|---|---|---|---|
| 3 (preferred) | 1 | 83.79 GiB | **105.0 GiB** | the probe's 12 GiB host-memory floor |
| 0 | 1 | 83.79 GiB | **105.0 GiB** | same |
| 2 | 0 | 41.89 GiB | **101.5 GiB** | same |

So the ceiling is **physical RAM (117.7 GiB), not either reported heap**, and
it is reached from a single memory type — there is no need to straddle heaps
and no evidence here about whether straddling would add anything.

**This is reservation, not residency.** No page was written, so it is an upper
bound on what the machine will hold. Residency has since been measured
separately and separately: `-bankgib 80` allocates **80 GiB in 23 buffers,
writes every page, and reads it at 237 GB/s** — past UD-Q4_K_XL's 82.52 GB
core. So live weights are demonstrated to 80 GiB and reservation to 105; the
band between them is the part still taken on trust.

## Reproducibility

Two full runs, 88 common rows (range arm + memory-type arm): **median ratio
1.0002, p10 0.9970, p90 1.0028**, worst cell 0.9915. Results in
[`results/bank.csv`](../results/bank.csv).

    go run ./cmd/bench -bankgib 64 -bankreadmib 1024 bank
    go run ./cmd/bench -bankgib 1 -bankheadroom 115 bank            # capacity, type 3
    go run ./cmd/bench -bankgib 1 -bankheadroom 115 -bankheadroomtype 2 bank

## What this changes

- **For the engine**: nothing to tune. Allocate from whatever
  `vk.NewBuffer` prefers; §5.1's "possibly free few percent on everything" is
  not there.
- **For LLM.md**: the capacity argument that ruled out Q5 and Q6 was wrong,
  and has been corrected. They are ruled out now by *throughput* — Q5 costs
  20% of tok/s and Q6 33% — which is a better argument, because it is the one
  that would still hold on a machine with more memory.
- **For `IDEAS.md` §5.2**: already closed by L0a. Between them there is now
  nothing left in section 5 except §5.3's texture-load lottery ticket.

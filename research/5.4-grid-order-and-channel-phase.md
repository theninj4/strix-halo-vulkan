### 5.4 The streaming kernels: the grid's fast axis decides which DRAM channels are busy — **done** ✅ (2026-09-30)

**Question** (KERNELS.md G6): every vertical's block is 6–14% norms,
packs, gates and copies that do no arithmetic, and the record held one of
them, the LLM's `hc.cn`, at "134 GB/s where a copy gets 236" with three
spent explanations (its reduction tree, its gamma read, the arena's memory
type). Put a bytes column in the profiles, list what is under 200 GB/s,
and fix or fuse it.

**What it was.** Two things, and neither is in a kernel's arithmetic.

**1. `hc.cn`'s 134 GB/s was an accounting error by a third.** P11 counted
80 KB a token: the residual once, the block output, gamma, the fp16 norm.
The residual is read *and written back* — 40 KB each way — and gamma comes
from the MALL, so the DRAM traffic is 110 KB a token, 901 MB at 8,192 rows
in 4.89 ms: **184 GB/s, 78% of a copy**. Priced by absence on the
standalone combine (`GUT` knobs, wrong by construction): dropping nine
tenths of the write-back saves 1.55 ms of 5.27, dropping the read 1.76,
dropping the block output's read 1.40 — three streams of the same size
costing the same. A copy's 236 is read plus write; an in-place update is
both too.

**2. The rest is §5.1b's coverage law, one level up: which rows are in
flight *together* is set by the dispatch grid's fast axis.** The DRAM
interleave is a 4 KB rotation over sixteen channels. A workgroup that reads
a slice of a row loads the channels that slice covers; the device runs the
next few dozen workgroups *in grid order* beside it; so if stepping the
grid's X axis moves the address by a whole number of rotations, everything
in flight is on the same channels.

- The LLM's residual is `[T][hc = 4][2560]` fp32. A stream's row is
  10,240 B, two and a half rotations: it asks the first half of the
  rotation for three bytes and the second for two. A token is 40,960 B,
  **ten rotations exactly**. `hc.norm` and `hc.combine` ran a grid of
  (token, stream) with the token on X, and `hc.cn` a workgroup a token
  walking its four streams in rough lockstep, so every workgroup in flight
  started on the same phase and the busier half of the channels saturated
  at 5/6 of the bus. Streams are 2,048 B of phase apart: walked
  stream-fastest, a token's four rows ask for the two halves evenly.
- The DiT family's q/k pack (`h3_qk_pack.comp`, `dit_qk_pack.comp`,
  `dit_pack_f16.comp`) is a workgroup a (token tile, head), reading 4 ×
  headDim bytes of each of sixteen rows. Where a row is a whole number of
  rotations — 56 heads × 512 B in H3's DiT, 32 × 512 in ACE's q, 8 × 512 in
  its k, 32 × 256 in the video VAE — one head of consecutive tokens is
  **an eighth (a sixteenth in the VAE) of the channels**, and the grid had
  the token tile on X. The image DiT's row is 3.75 rotations, so its one
  head lands on four phases, half the channels.

The test that separated this from everything tried before is one line: the
same grid, the same workgroups, the same bytes, walked in the other order
(`id = x + y·NX; stream = id % hc; token = id / hc` in the norm). Three
other arms on the same kernel moved nothing at DRAM sizes, which is why the
earlier hypotheses all died: every load of a row issued at once (`HOIST`),
sixteen bytes a lane in one wave a row (`HOIST=2`, bit-exact by keeping the
256 strided partials as `vec4` lanes), and both together.

**What shipped.** Every change is the same workgroups doing the same
arithmetic, so every gate is bit-identity.

*The LLM* (`llm_hc_norm`, `llm_hc_combine`, `llm_hc_cn`): the grid is a
stream across and a token down, and `hc.cn` is a workgroup a (token,
stream) at every width — P11's walk and P16's row threshold
(`hcCNSplitRows`, `LLM_HC_CN_SPLIT_ROWS`) are gone. The block output row
the four streams share is still fetched from DRAM once, because the four
workgroups that read it now run back to back; on the old grid they were
T workgroups apart, which was a third of the standalone combine's traffic.
All three issue a row's loads before anything waits on one (`HOIST`,
default on): the loops were `for (i = tid; i < n; i += 256)`, which is not
unrolled, so one 256-byte request a wave, and the read-modify-write through
one binding compiled to load, `s_waitcnt vmcnt(0)`, store, ten times over.
That is nothing at DRAM sizes and everything at decode.

**The rule.** For a kernel that reads a slice of each row a workgroup:
take the address step along the grid's X axis; if `gcd(step, 4096)` is
larger than the slice, the workgroups in flight miss channels. Put the
axis with the *small* step on X. Rows that are a whole number of 4 KB
rotations (any width that is a multiple of 1,024 floats, or of 2,048
halves) are the ones that bite, which is most of them. The profile's GB/s
column finds them: anything near 120 on a pass that does no arithmetic is
this, and the accounting must count an in-place update twice.

**Refused.** `vec4` lanes (nothing, then −2% once the grid is right). The
walk with the start rotated a stream a token (`ROTATE`: 4,752 µs where the
stream-fastest grid gets 4,620). A one-wave workgroup. **Not done:** the
gate fused with the norm that follows it (one read of the residual saved,
about a fifth of those two passes' traffic: ~1.5% of a music forward, less
of a video one; the run and chunk structure differ a host), the hoisted
gate on the hosts that did not re-run their gates (`DiTGateAdd` is still
the plain loop for qimage, kev, ocr, zimage, ace/lm), the head-fastest
packs for `zimage/qwen` and `parakeet` (their rows are 2.5 and ~1 rotations:
predicted short, not measured), and the LLM's `move`, `moe.combine`,
`dn.*` and `ple.*` passes, whose grids already have the small step on X
and whose rates were not measured here. The image DiT's gate reads 175 GB/s
in its profile and was not looked at.

**Tools.** `LLM_HC_SPV=cn=…,norm=…,combine=…` (a build of an hc kernel from
disk); `-DTOKEN_FAST=1`, `-DHOIST=0`, `-DGUT=1|2|3` on the three hc
shaders; `-DHEAD_X` on the packs; `-DHOIST` on `h3_norm_mod.comp` and
`dit_gate_add.comp`; the `Bytes` field on the `Stage` of `h3/dit`,

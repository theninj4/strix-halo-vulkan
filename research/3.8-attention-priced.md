### 3.8 The transposed attention priced: the softmax is 7 points, the memory side 12, and the register allocator decides the rest — no exact arm beats the shipped build; the kernel opt-in on the image DiT — **done** ✅ (2026-09-30)

**Question** (KERNELS.md G4, A1–A3): `h3_attn_t.comp`'s shipped build
(`QT2 KTIL4`, wave32) runs at 37–38 TFLOP/s, 68–75% per clock, with 112
VGPRs spilled to scratch and LDS. M11c's gutting of the *plain* kernel
read 65.7 TFLOP/s on its last arm, above the ceiling, so the compiler had
dropped MMAs and nobody knows what the transposed loop's floor is. What
does each part of the loop cost, honestly (every arm's result kept live),
and which of the plan's levers — the spill, a head split, wave64, lazy
rescaling — buys anything?

**Answer: the floor is 79–81% per clock with real loads and 87–90% with
L0 hits; the softmax is 6–7 points, the K/V loads 11–12, and everything
exact that was built lands inside ±2% of the shipped build**, because at
256 VGPRs the register allocator's moves around the MMAs change with
every edit and cost as much as the edit saves. The only carry that moved
a number is the kernel itself onto the image DiT (1.07x on its
attention, 1.7% on a step), and it is opt-in there: exact at the fp16
level, but the edit oracle's prefill bound sits within 2x of its own
sensitivity floor and the kernel's rounding pattern tips it.

#### The ISA first (G-o9)

`RADV_DEBUG=asm go run ./cmd/probe shaders/h3_attn_t_qt2_kt4.spv 32`,
one key block (128 MMAs: 64 for S^T, 64 for O^T), counting only the path
a whole block executes:

| class | shipped | what it is |
|---|---:|---|
| non-MMA VALU, total | **911** | 7.1 an MMA |
| `v_mov` / `v_dual_mov` / `v_swap` | 197 | the allocator rotating registers so the next V fragments can land while these MMAs run |
| `v_cndmask` (+ dual) | 176 | the tail mask on P (64, compiled into every block), the half-wave exchange's selects (64), the rest |
| `v_cmp` | 32 | the tail mask's compares, every block |
| `v_max3` / `v_max` | 98 | the row max: a **16-deep dependent chain** a query tile |
| `v_permlanex16` | 34 | the exchange (32) and the max (2) |
| `v_exp`, `v_cvt_f16`, `v_mul` | 66 / 64 / 92 | the softmax's own work |
| `v_add_nc` | 88 | fragment addresses |
| scratch + LDS reloads | 65 + 48 | the spilled Q^T read back every block (ACO spills to LDS first, then scratch) |
| `buffer_load_b128` | 128 | 32 K and 32 V fragments, two loads each |

The head-64 VAE build (`h3vae_attn_t_hd64_qt2_kt4`, spill-free at 240)
carries 925 non-MMA VALU a block against 64 MMAs: 14.5 an MMA, because
the softmax is the same work for half the matrix work.

At 768p (38,247 keys, ~2600 MHz): shipped 1.192 s (35.2), the best arm
1.175 s (35.7). The two builds execute 135 fewer VALU and 113 fewer
reloads a block for the same time, so **the instruction count is not the
price** on this kernel (as §2.13 found on the MoE GEMM): with 4–5 waves
a SIMD one wave's VALU overlaps another's MMAs, and what a source change
does to the allocation — `TAIL_SPLIT` alone adds 70 `v_swap` a block for
its −111 VALU — is as large as what it saves.

**The honest gutting** (each phase removed with its result kept live: P^T
still feeds the MMAs, O^T is still stored), on the spill-free
`QLDS TAIL_SPLIT` base (202.1 ms):

| taken away | ms | of the base |
|---|---:|---:|
| the online rescale of O^T (`GUT_CORR`) | 196.3 | 3% |
| the exp2 (`GUT_EXP`) | 199.9 | 1% |
| the row max (`GUT_MAX`) | 187.3 | 7% |
| the whole softmax, exchange kept (`GUT_SOFTMAX`) | 180.1 / 179.7 | **11%** |
| … and the exchange (`GUT_XCHG`): MMAs and loads alone | 178.7 / 176.3 | 12–13%; **41.3 TFLOP/s, 81% per clock** |

So A2 (lazy rescaling) is bounded at 3 points and the exact version of it
(`LAZY`) buys nothing net; the row max's 7 points are its dependent
chain, and `MAX_TREE` buys nothing net either. **The floor of this loop
structure is 81% per clock with real loads.**

**The memory side** (`L0_LOADS`: every K and V fragment load reads the
first key block, so the loads are issued and waited for as before but
every one is an L0 hit; wrong by construction, timed):

| | real loads | `L0_LOADS` | |
|---|---:|---:|---|
| shipped (spilled) | 194.9 | 189.3 | 3%: the scratch reloads are not K/V |
| `QLDS TAIL_SPLIT PV_ORDER MAX_TREE LAZY` | 197.5 | **173.8** | **12%**, 41.9 TFLOP/s, 82% |
| `GUT_SOFTMAX` | 179.7 | 168.4 | 43.3, 85% |
| the floor | 176.3 | **162.4** | **44.8, 87.5%** |
| 768p, the same four | 1.192 / 1.175 / 1.109 / 1.114 s | 1.060 / 1.029 / 0.963 / **0.933** s | floor + L0: **45.0 TFLOP/s, 90%** |

The decomposition of the spill-free kernel at 480p: **K/V loads 12
points, softmax 6, the in-wave floor 82–87%** (128 fragment loads, 130
allocator moves and 80 address adds beside 128 MMAs). That is the GEMM's
G1 picture again — ~10 memory points, then the schedule — and the lever
that took the GEMM's memory points was §2.9: the slab fetched once a
workgroup a block ahead and shared through LDS at wave32.

#### What that lever would take here, and why it was not built today

A workgroup of W waves sharing each key block's K and V tiles (32 KB a
block at KTIL4, head 128). Staging a block ahead through registers, as
§2.9 does, costs 32 KB / (32 W) bytes a lane: 32 VGPRs at W = 8, which
does not fit beside `QT2`'s 128 accumulators (the shipped build is at 256
with 112 spilled), so the wave drops to `QT1` (O^T 64, S^T 32, P^T 32,
staging 32: ~190) and reads four `ds_load_b64` a fragment at one fragment
an MMA — twice the GEMM's ratio, whose reads §2.10 priced at 3%, so ~6 —
plus a barrier a block (the GEMM's barrier-and-reads together were 9). Net
expected: the 12 memory points less 6–9, on a kernel that is 33% of a
video forward: **≤ 2% of a forward for a session's build.** Decision 7's
plateau is reached on the exact arms (five consecutive inside ±2%), so
this is recorded as the one structural lever left (G4b) and not built.

**Dead by arithmetic, so not built:** a head-dimension split (S^T needs
all 128 channels, so two passes of 64 recompute it: 1.5x the MMAs);
wave64 for the transposed kernel (a VALU instruction is two passes at
wave64 and the softmax is 7 VALU an MMA; A/B fragments move 4x their
bytes; §6.2 measured the plain kernel 1.40x slower at wave64 for the same
reasons, and G-o4's element order is moot).

#### The carry-in: the image DiT (opt-in, held by the edit gate)

`qimage/dit` runs `dit_attention_wmma.comp` (`QT1 KTIL4`, wave32, fp32
context out) and then a "narrow ctx" pass to fp16. It can now run
`qimage_attn_t_qt2_kt4` (`h3_attn_t.comp`, `STORE_TAIL=0`) instead:
`QIMAGE_ATTN_T=1` at process start, the element order probed at the first
graph through `h3/dit.TransposedAttentionOK` (staging still submits
nothing), the context written fp16 at the output projection's stride, and
"narrow ctx" kept only for the causal text passes' rows in an edit
prefill. `STORE_TAIL=0` gained the bound the plain kernel's fp32 store
has: the tile the sequence ends inside is stored one query a lane (each
lane owns a query outright), because the edit prefill repairs the prefix
one segment at a time with the key count cut to the segment's end, and
a whole-tile store past that end overwrote the next segment's finished
rows. The video VAE's five head-64 builds carry the same bound
(`TestGPUDecoder`: PSNR 81.7 dB, unchanged).

`TestGPUStepProfile`, 1024² (4,096 image rows + the prompt), the int8
bank:

| | attention, 32 layers | TFLOP/s | a cached step | a prefill |
|---|---:|---:|---:|---:|
| plain `QT1 KTIL4` wave32 (the default) | 248 ms | 35.7 | 1.908 s | 1.966 s |
| **transposed `QT2 KTIL4`** (`QIMAGE_ATTN_T=1`) | **232 ms** | **38.3** | **1.876 s** | 1.934 s |

1.07x on the kernel, not H3's 1.55x: the image DiT's plain kernel was
already at 35.7 on its 4k-key sequences where H3's plain build reads 24
at 16k.

**The gates.** `TestGPUOracle256` and `TestGPUOracle1024` (40
teacher-forced and free-running steps) pass on the transposed build.
**`TestGPUEditOracle` does not**: the teacher-forced prefill reads rel
7.9e-2 against its 2e-2 bound (rms 2.4e-3, 0.41x the released bf16
pipeline's own error), where the plain kernel reads 7.7e-3; the cached
steps after it are the plain kernel's (6e-4, 9e-4, 2.4e-4), and the
free-running four steps end at rel 1.5e-2 (rms 4e-3) against the plain
kernel's 2.2e-3. Where it comes from, block by block (the fp16 context
plane dumped after block N's attention under each kernel, the same
inputs, the same step):

| | rms rel | max rel | note |
|---|---:|---:|---|
| block 0, transposed against plain | **8.1e-5** | 1.5e-4 | fp16 rounding, H3's 9.7e-5; the causal text rows identical |
| block 19, transposed **at that block only**, plain everywhere before it | **1.1e-4** | 2.4e-4 | the kernel on identical inputs: exact |
| blocks 10 / 15 / 16 / 17 / 18 / 19 / 20, transposed throughout | | 6e-4 / 1.4e-3 / 1.6e-3 / 1.1e-2 / 1.5e-2 / 2.3e-2 / **1.7e-1** | target rows 288, 304, 513 (image rows 0–1 and 14, columns 11–12); the prefix rows stay at ≤ 1.6e-3 |
| the plain `QT1 KTIL8` wave64 build on the main pass (a plain-family fp16 perturbation of the target rows) | | 7e-5 → 3e-3 by block 30 | the gate reads 8.4e-3 |
| the same build on the prefix passes (the prefix rows perturbed instead) | | | the gate reads **1.73e-2** |
| transposed main pass only / prefix passes only / both | | | 1.74e-2 / 1.06e-2 / **7.9e-2** |

So the kernel is exact at the fp16 level at every block on identical
inputs, and this edit's prefill amplifies an fp16-level difference in the
*prefix* rows ~100x at three target rows between blocks 16 and 20: a
perturbation from the plain kernel's own family lands at 1.73e-2 against
the 2e-2 bound, and the transposed kernel's, ~3x larger at the kernel
(8.1e-5 against 2.7e-5 rms), at 7.9e-2. The gate is within 2x of its
sensitivity floor for edits, and it is the vertical's gate, so **the
transposed kernel is opt-in for the image DiT, not the default**: 1.7% of
a step, held until the image vertical decides whether its edit bound
measures the kernel or the input. Nothing served changes.

Not carried: `ace/dit`'s full attention (grouped-query heads, which
`h3_attn_t.comp` does not map; its attention is a small share of a music
step), the speech encoders (short clips, tiny), the VAE's exact arms
(spill-free already; the same knobs apply and were not screened).

**Tools left in the tree:** on `h3_attn_t.comp`, `TAIL_SPLIT`, `QLDS` /
`Q_LPITCH`, `PV_ORDER`, `MAX_TREE`, `LAZY` (exact), and the controls
`L0_LOADS`, `GUT_CORR/EXP/MAX/SOFTMAX/XCHG` (wrong by construction); the
key block is `shaders/h3_attn_t_block.glsl`, included once for whole
blocks and once for the tail. The default build's ISA is unchanged (the
restructure is a no-op without the knobs: the SPIR-V differs only in its
ID bound). `H3_ATTN_ONLY_SPV` now puts the shipped transposed build
second and reports "bits: identical" per arm. Screens:
`scratchpad/screen{1,2,3,768}.samples` for the clocks.
